## CVC-DEEPLINK-1 — the scheme the CVC installer registers is refused by every deep-link parser

**Severity:** High (the registered protocol is unusable end to end).

**Trigger.** On a packaged CVC Studio build, open a link on the protocol the
build registers — `cvc-studio://connect?token=<compact JWS>` — or paste one
into the connect-link flow.

**Expected.** The link is accepted and verified, exactly as `openwork://connect`
is in an upstream OpenWork build.

**Actual.** The link is dropped. The desktop parsers and the renderer parser
each accept only the hardcoded upstream schemes `openwork:` and
`openwork-dev:`, so the URL is refused before signature verification and the
connect prompt never appears.

**Affected files (before the fix).**

- `apps/desktop/electron/connect-link.mjs` — `extractConnectLinkToken` and
  `extractConnectExchange` compared `parsed.protocol` against the two literal
  upstream schemes.
- `apps/app/src/app/lib/openwork-links.ts` — `parseConnectDeepLink` and
  `parseChatDeepLink` did the same.

**Why the four surrounding pieces already agreed on `cvc-studio`.** The
distribution declares `protocolScheme: "cvc-studio"`; the packaged app calls
`app.setAsDefaultProtocolClient("cvc-studio")`; the Electron Builder config
registers `cvc-studio` under `protocols`; and `forwardedDeepLinks` in
`main.mjs` already accepts `${DESKTOP_PROTOCOL_SCHEME}://` and queues the URL
to the renderer. Only the parsers disagreed, which is what made the failure
silent: the operating system handed the URL over correctly and the application
then discarded it.

**Reproduction.**

```text
node --test apps/desktop/electron/cvc-isolation.test.mjs
  ✖ CVC deep-link parsers accept the protocol scheme its installer registers
bun test --isolate tests/cvc-deep-links.test.ts
  ✖ the CVC renderer accepts the deep-link scheme its installer registers
```

Both fail on `df873e29` and pass on this branch.

**Fix.** The scheme set is now an explicit input instead of a hardcoded pair,
so a distribution's registered scheme reaches the parser:

- `connect-link.mjs` takes an optional `schemes` option (default: the upstream
  pair, so callers that pass nothing keep today's behaviour) on
  `extractConnectLinkToken`, `extractConnectExchange`, `verifyConnectLinkUrl`
  and `resolveConnectExchangeUrl`.
- `main.mjs` derives one `DEEP_LINK_PROTOCOLS` constant from
  `DESKTOP_PROTOCOL_SCHEME` and passes it to those parsers and to
  `forwardedDeepLinks`. For every upstream flavour this is character-for-character
  the previous set.
- `openwork-links.ts` accepts the CVC scheme when the renderer is a CVC build,
  reusing the existing build-time switch that already pins the CVC app name.

**Impact if unfixed.** CVC Studio registers a protocol handler it cannot
consume. Enterprise/organization onboarding through a connect link cannot
complete on a CVC install, and Den chat handoffs are dropped the same way.

## CVC-DEEPLINK-2 — the in-app browser hands off only `openwork://`

**Severity:** Medium.

**Trigger.** On a CVC build, follow a `cvc-studio://…` link inside the built-in
browser panel (for example a page offering an `openwork`-style desktop handoff).

**Expected.** The navigation is intercepted and relayed to the deep-link queue,
and the tab is cleared so the custom scheme cannot error — the behaviour
OpenWork gets for `openwork://`.

**Actual.** The interception predicate in `browser-panel.mjs` tested
`startsWith("openwork://") || startsWith("openwork-dev://")`. A CVC link falls
through to normal navigation handling, so the handoff never happens and the tab
attempts a load of a scheme the web contents cannot open.

**Affected file.** `apps/desktop/electron/browser-panel.mjs` (the
`did-start-navigation` handler).

**Reproduction.**

```text
node --test --test-name-pattern='in-app navigation is handed off' \
  apps/desktop/electron/browser-panel.test.mjs
  ✖ in-app navigation is handed off for the scheme the distribution registers
```

Fails on `df873e29`, passes on this branch.

**Fix.** `createBrowserPanel` takes `deepLinkProtocols` (default: the upstream
pair) and matches against it. `main.mjs` passes the same
`DEEP_LINK_PROTOCOLS` it now gives the parsers, so the OS-level handler, the
in-app interception and the parsers cannot drift apart again.

## CVC-LAUNCHER-1 — `scripts/cvc.mjs` validates the mode through the prototype chain

**Severity:** Low (no privilege change; the documented usage error is bypassed).

**Trigger.** `node scripts/cvc.mjs constructor` (also `toString`, `valueOf`,
`hasOwnProperty`, `__proto__`).

**Expected.** The usage error, as for any other unknown mode.

**Actual.** `parseArgs` guarded on `!commands[mode]`. Those names are truthy on
`Object.prototype`, so validation passed and the failure surfaced later as
`TypeError: commands[mode].map is not a function`. `--dry-run` failed the same
way, so the dry-run inspection path inherited the wrong error too.

**Affected file.** `scripts/cvc.mjs`.

**Reproduction.**

```text
node --test scripts/cvc.test.mjs
  ✖ CVC argument parsing ignores Object.prototype keys as modes
```

Fails on `df873e29`, passes on this branch.

**Fix.** `Object.hasOwn(commands, mode)` — the launcher's own command table is
the only accepted source of modes.

## CVC-BRAND-1 — a persisted brand name still renames the CVC application

**Severity:** Medium. Reported, deliberately not changed.

**Observed behaviour.** The renderer pins the CVC identity: `normalizeShellConfig`
forces `appName`, `docsButton`, `feedbackButton` and `cloudSignin` on every
read, update and reset, and `shell-config.tsx` restores the window title. The
desktop main process does not apply the same restriction to the bootstrap
branding override:

```js
// apps/desktop/electron/main.mjs
currentDisplayAppName = applyBrandAppName(
  BLANK_SLATE_LAUNCH.enabled || DESKTOP_DISTRIBUTION.flavor === "enterprise"
    ? null
    : bootstrapConfig.brandAppName,
  { … updateElectronAppName: true … },
);
```

`flavor === "cvc"` is not `"enterprise"`, so a `brandAppName` present in the
CVC profile's `desktop-bootstrap.json` is applied through `app.setName`,
`applicationMenu.setAppName` and `window.setTitle`. `brandAppName` is written
by the connect-link path (`connect-link.mjs` → `persistConnectLinkClaims` →
`workspace-store.mjs`), so accepting an organization connect link can rename
the CVC application at the operating-system level even though the renderer
keeps saying "CVC Studio".

**Why it was not changed.** Whether CVC Studio should accept organization
branding at all is a product decision — the same connect-link flow is a
retained, intentional OpenWork feature. Two candidate directions, for the
primary agent to choose:

1. treat `cvc` like `enterprise` in that condition, pinning the desktop name to
   the distribution's `appName`; or
2. keep organization branding but record it as intended and make the renderer
   stop pinning the name, so the two surfaces agree.

Until one is chosen the two surfaces disagree, and the disagreement is silent.

## Areas checked and found sound

Each item below was exercised, not merely searched for.

**Updater and recovery isolation.** Calling `registerUpdaterIpc` with
`updatesEnabled: CVC_DESKTOP_DISTRIBUTION.updatesEnabled` registers all ten
`recovery:*` and `updater:*` channels as explicit refusals, never loads the
native updater, and never touches `app.getPath`/`app.getVersion` (asserted by
passing throwing doubles). `ensureAutoUpdater()` resolves to `null`.

**Accidental upstream publish/update destinations.** The focused Electron
Builder test in `scripts/cvc.test.mjs` loads the real Electron Builder 26.15.3
configuration loader against `electron-builder.cvc.yml`. The resolved
configuration inherits file/resource, target, signing-hook and native-runtime
rules from `electron-builder.base.yml`, sets app ID `local.cvc.studio`,
product name `CVC Studio`, Linux executable `cvc-studio` and the `cvc-studio`
protocol, and resolves `publish` to `null` — the base file's GitHub publisher
for `different-ai/openwork` is not inherited. Note that this test is skipped
when the desktop dependency closure is not installed, so it is only evidence in
a full checkout; it ran here.

**Hardcoded upstream release URLs.** `RELEASE_DOWNLOAD_BASE_URL`,
`RELEASE_PAGE_URL` and the `recovery.mjs` GitHub paths still name
`different-ai/openwork`, but every reachable use is behind
`DESKTOP_DISTRIBUTION.updatesEnabled`. `resolveArchitectureInfo` returns empty
`downloadUrl` and `releaseUrl` for CVC and does not fetch the release manifest.
`recovery.mjs` is imported only by `updater.mjs`, which returns early.

**Telemetry.** `initOpenworkSentry` returns before reading any build config for
a distribution with `telemetryEnabled: false` (asserted with an `app` whose
`isPackaged` getter throws). The launcher also builds the renderer with
`VITE_OPENWORK_POSTHOG_KEY` and `VITE_OPENWORK_SENTRY_DSN` emptied and
`OPENWORK_DESKTOP_SENTRY_DISABLED=1`.

**Factory reset, container cleanup and Linux integration.** All three shared
cleanup commands throw for CVC, `runPendingNukeCleanup` is skipped at startup,
and `createLinuxDesktopIntegration` reports `supported: false` so upstream
AppImage repair cannot modify a CVC install.

**Dry-run credential exposure.** With hostile inherited values set
(`VITE_OPENWORK_POSTHOG_KEY`, `VITE_OPENWORK_SENTRY_DSN`,
`OPENWORK_DESKTOP_SENTRY_DSN`, `OPENWORK_ELECTRON_PROTOCOL_SCHEME`),
`node scripts/cvc.mjs package --dry-run` printed only the fixed CVC values: the
PostHog and Sentry variables empty and the protocol scheme `cvc-studio`. The
dry-run whitelist is the union of `cvcEnvironment` and
`developmentEnvironmentKeys`, and no member of either can hold a credential.
No leak found.

**Native-module compatibility probe.** Running
`apps/desktop/scripts/verify-electron-native.cjs` under the Electron 43.2.0
Node runtime prints `cvc-native-ready` and exits 0 in this checkout, so both
`better-sqlite3` and `node-pty` load against Electron's ABI. The probe covers
both modules the runtime needs, which is what makes it a real precondition
rather than a version check.

**Renderer identity normalisation.** `readShellConfig` applies
`normalizeShellConfig`, so a persisted `openwork.shell-config` carrying
`appName: "OpenWork"` and `cloudSignin: true` cannot restore the upstream
product name or the hosted sign-in affordance on a CVC first boot.

**Windows launcher routing.** pnpm is invoked as `cmd.exe /d /s /c pnpm.cmd …`
with `shell: false` and a fixed argument list; no user argument is interpolated
into a shell string. Production modes scrub the documented development
switches and every `OPENWORK_EVAL_*` variable.

## Recorded but not changed

- `scripts/cvc.mjs` sets `OPENWORK_ELECTRON_PROTOCOL_SCHEME=cvc-studio`, but no
  runtime code reads that variable: `main.mjs` takes the scheme from
  `desktop-distribution.mjs`. Harmless today (both values agree) and now no
  longer misleading for deep links, since `DEEP_LINK_PROTOCOLS` is derived from
  the distribution. Worth either reading it or dropping it; changing it would
  alter precedence, which is an architectural choice.
- `apps/desktop/build/installer.cvc.nsh` deletes the path stored in
  `%APPDATA%\local.cvc.studio\windows-brand-shortcut.txt`. The path is a file in
  the user's own roaming profile that the same user can already edit, and the
  macro mirrors the upstream `installer.nsh`. No privilege boundary is crossed;
  no change made.
- `pnpm --filter @openwork/desktop run rebuild:electron-native` rebuilds only
  `better-sqlite3` (`electron-rebuild --force --which-module better-sqlite3`),
  while the probe checks `better-sqlite3` **and** `node-pty`. If `node-pty`
  alone were ABI-incompatible, the probe would fail, the fallback would rebuild
  the wrong module, and the next launch would probe and rebuild again — a slow
  loop rather than a wrong result. It is not a confirmed defect: both modules
  load under Electron here. Flagged because the fallback does not cover the
  whole condition the probe tests.
- The CVC Artifact still ships upstream icons and secondary labels, as the build
  review already states. Out of scope for a bug audit.

## Remaining risks and limitations

- No signed installer or packaged-artifact smoke test was produced. Everything
  here is source-level or development-profile evidence. The protocol fix is
  verified at the parser boundary and in the in-app browser handler, not by
  installing a CVC build and clicking a real `cvc-studio://` link.
- `DEEP_LINK_PROTOCOLS` is derived from `app.isPackaged` at module load in
  `main.mjs`, which cannot be exercised by a unit test; the parsers and the
  browser panel are tested directly with the same value the distribution
  produces.
- The macOS and Linux paths were not exercised at all beyond reading the
  configuration; this audit ran on Windows only.
- The CVC renderer still contains the full inherited cloud surface. This audit
  confirms specific boundaries (updater, recovery, telemetry, factory reset,
  Linux integration, shell identity) and does not claim the application is
  local-only.
- The organization-signing and connect-link key material is unchanged and was
  not audited.
